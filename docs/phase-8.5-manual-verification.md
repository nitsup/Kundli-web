# Phase 8.5 — Manual Verification and Human Audit Gate

## Purpose and status

This audit separates three claims that must not be conflated:

1. **Computational correctness:** code follows the documented, encoded rule in covered inputs.
2. **External correctness:** output agrees with an independent astronomical/reference source under matching settings.
3. **Methodological correctness:** selected astronomical settings and domain rules are the intended Kundli-Web methodology.

Passing automated tests supports the first claim only. It does not establish the second or third. This audit did not run an independent ephemeris, obtain a domain review, perform a legal review, or deploy to production. Accordingly, no comparison is recorded as passed and no phase is declared fully verified.

The implementation's normal `CalculationResult` adds `generatedAt`/`createdAt` timestamps. Repeated runs can therefore differ in metadata even when the deterministic calculation identity and astronomy are the same. The calculation hash excludes the display name, but includes the `birthProfileId`; result input still carries the name. Do not compare whole serialized objects when checking identity independence.

## Classification and evidence rules

Each matrix row has exactly one verification-class classification:

- `AUTOMATED SUFFICIENT FOR INTERNAL INVARIANT`
- `MANUAL CHECK REQUIRED`
- `INDEPENDENT REFERENCE REQUIRED`
- `PRODUCTION VERIFICATION REQUIRED`
- `METHODOLOGY / DOMAIN REVIEW REQUIRED`
- `MULTIPLE VERIFICATION TYPES REQUIRED`

Statuses are separate from those classifications. `LOCALLY VERIFIED` means a local automated/runtime check has actually been observed; it is not a claim of independent or methodological correctness. `UNVERIFIED` means the required evidence has not been recorded. `INDEPENDENTLY VERIFIED` requires an independent source and reproducible comparison record. `PRODUCTION VERIFIED` requires evidence from the actual deployed target. No item in this audit is marked independently or production verified.

For every independent comparison, record the source/tool and version, all configuration/settings, exact input, expected output, actual output, units, tolerance and its justification, result, date, and methodological differences. A second function in this repository, or another result from the same Swiss provider, is not an independent reference.

### Actual calculation paths inspected

**Natal path:** `astrologyEngineContract.calculate` → `swissEphemerisProvider.calculate` → validated `CalculationInput` and fixed `calculationConfigurationSchema` → UTC `Date` → wrapper `dateToJulianDay` → Swiss provider. The provider resolves the package's ephemeris directory, requires `sepl_18.se1`, `semo_18.se1`, and `seas_18.se1`, hashes them, and sets the path. It calculates with `CalculationFlag.SwissEphemeris | CalculationFlag.Speed`; sidereal calls add `CalculationFlag.Sidereal`. It sets `SiderealMode.Lahiri`, asks for `LunarPoint.TrueNode`, rejects returned Moshier flags, calculates houses using coordinates in latitude-then-longitude argument order and `HouseSystem.WholeSign`, subtracts ayanamsha from tropical angles, and derives Ketu as Rahu + 180 degrees. These are source-inspection findings, not independent proof of wrapper/API semantics or astronomical accuracy.

**Transit path:** `calculateTransits` validates an explicit offset-bearing instant and coordinates, converts that instant to canonical UTC, and calls `swissEphemerisProvider.calculateAt`. That method validates the fixed configuration and canonical UTC timestamp, calculates Julian day, and enters the same `calculateAtJulianDay` implementation used by natal calculation. It does not use `new Date()` as an input or current-time default. Local tests compare equivalent offset strings and deterministic repeated calls; no independent ephemeris comparison has been performed.

**Input/time path:** `createCalculationInput` requires a full location object. `resolveLocalBirthTime` validates Gregorian civil date/time and IANA timezone, discovers candidate offsets using runtime `Intl` timezone data, rejects gaps, and requires an earlier/later choice for folds. The resolved UTC instant and offset are schema-checked. Coordinates are range-checked but not geocoded or provenance-verified.
